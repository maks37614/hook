# Персональні сповіщення hook2

Сервер працює постійно. Браузер потрібен для налаштування правил, але не для їх виконання. Сповіщення та фонове стеження виконуються лише під час чинного пробного або оплаченого повного доступу. Після завершення строку налаштування зберігаються, робота призупиняється; продовження — через [персональний код](access-management.md).

## Що реалізовано

- Власник запиту визначається за перевіреним Firebase ID token або серверною сесією. Чужий `userId` відхиляється.
- Один серверний Telegram-бот. Користувач натискає «Підключити Telegram», відкриває одноразове посилання і натискає Start.
- Посилання живе 10 хвилин. На сервері зберігається його SHA-256, а не секрет. Підключення можливе лише з особистого чату самого користувача. Один Telegram-акаунт прив’язується до одного акаунта сайту.
- Цінові правила Binance/Bybit, spot/futures виконуються кожні 5 секунд; дані іншої біржі/ринку не підміняють джерело. Одну котировку використовують усі користувачі з цим інструментом; одночасно виконується до 8 запитів.
- Стеження працює у серверних воркерах і перевірках свічок. Активні монети відновлюються при запуску. Вимкнення монети, Telegram або категорії скасовує ще не надіслані повідомлення стеження.
- Усі робочі повідомлення цін/стеження проходять через збережену чергу. Тестове повідомлення надсилається безпосередньо й повертає фактичний результат.
- Черга повторює мережеві збої, 5xx та 429, враховує `retry_after`, обмежує швидкість на бота/чат і відновлюється з диска. Успішні частини довгого повідомлення зберігаються окремо.
- Цінова подія очікує доставки до 7 днів, подія стеження — до 1 години, щоб не надсилати застарілі сигнали. 400/403/404 позначаються як остаточна помилка. 401 повторюється, дозволяючи адміністратору замінити токен.
- При відключенні Telegram очікувана доставка скасовується. Після повторного підключення майбутні правила продовжують діяти.

Скринерний cron оновлює дані патернів, але сам не створює нової масової Telegram-підписки: сповіщення надходять за правилами й монетами, які вибрав користувач. Звуки і браузерні push/toast працюють при відкритому сайті; доставка Telegram працює незалежно від вкладки.

## VPS OVHcloud і автоматичні оновлення

Основний хостинг — `https://h00k.top` на VPS `57.129.171.244`. Docker запускає один серверний процес; Caddy забезпечує HTTPS. Постійні дані зберігаються у Docker volume, окремо від Git та образів.

- [Одноразове встановлення та автодеплой з main](vps-auto-deploy.md)
- [Google-вхід: Firebase, Google Cloud, callback і налаштування VPS](google-auth-vps.md)

VPS перевіряє main приблизно щохвилини та запускає лише commit з успішним Validate. Перед заміною робиться резервна копія даних; при невдалому запуску агент повертає попередній image. Логи обмежені трьома файлами по 10 MB.

## Перенесення наявних даних

Отримайте актуальну резервну копію `DATA_DIR` старого сервера при зупиненому записі. Перенесіть усі JSON разом, включно з `deleted_alerts.json`, `accounts.json`, `telegram_links.json`, `notification_outbox.json` і даними cooldown, якщо вони існують. Зберігайте власників і стан видалених правил. Імпортуйте копію лише в порожній том до першого запуску; користувач `node` (UID 1000) у контейнері має мати доступ до файлів.

Автоматичне відновлення з `BOOTSTRAP_*` або Git вимкнене: старий snapshot не повинен відновлювати видалені правила. Не поєднуйте старі масиви з новими даними вже запущеного сервера. Дані Firestore синхронізуються при вході власника; для негайного фонового моніторингу без входу потрібна серверна міграція.

## Один процес моніторингу

JSON-сховище призначене для одного процесу. Не запускайте PM2 cluster, кілька контейнерів чи паралельних deployment з одним томом. Для горизонтального масштабування потрібні спільна БД, централізована черга й один споживач Telegram updates. Старий Railway видалений; нові робочі версії встановлюються на VPS.

## Telegram

Використовується long polling. Тому для цього бота не має бути активного webhook чи іншого процесу `getUpdates`. Перевірте `getWebhookInfo`; якщо webhook належить іншому вашому додатку, використайте окремого бота. Сервер не видаляє сторонні webhook автоматично. Токен зберігається лише на сервері; браузер його не отримує. Telegram chat_id ніколи не береться зі спільних налаштувань як fallback для користувача.

Якщо бот заблокований, черга показує помилку. Після розблокування надішліть тест і заново активуйте потрібне одноразове правило. Завершені невдалі події не відправляються автоматично як нові сигнали.

## Вхід та міграція

Google-вхід та вхід чинних Firebase email акаунтів збережено. Нова реєстрація через email і основний email-вхід використовують серверні акаунти: scrypt із сіллю, випадкові ID, непрозорі токени сесій, 30-денний термін і відкликання при виході. Пароль такого акаунта має містити щонайменше 8 символів.

Старі браузерні «акаунти» з `btoa(password)` не були справжньою перевіркою особи. Вони не можуть отримати доступ до серверних персональних даних. Для них потрібна нова серверна реєстрація або Firebase вхід; не переносіть їхні старі ID без підтвердження власника.

Токени й персональні JSON більше не повинні бути в Git. Якщо токен вже потрапив до попереднього commit, видалення поточного файлу не видаляє історію: перевипустіть токен через BotFather і встановіть нове значення `TELEGRAM_BOT_TOKEN` на сервері.

## Перевірка і межі гарантій

`npm ci`, `npm run lint`, `npm test`, `npm run build`. Нові тести покривають двох користувачів, підробку власника, Firebase підпис/claims, локальний пароль/сесію, одноразові/прострочені посилання, offset polling, stale sync, 429, блокування бота, довгі повідомлення, перезапуск черги, паузи й повторну активацію. Окремий HTTP-тест створює два акаунти та Telegram-прив’язки, запускає реальні cron/outbox без ручного тригера, імітує 503 Telegram та SIGKILL сервера, перевіряє повторну доставку після старту, ізоляцію історії й відновлення активного воркера. Зовнішні API в тестах замінені локальним HTTP-сервером. Десять сценаріїв автодеплою перевіряють CI gate, збереження даних, backup, відкат і повторні спроби. GitHub Validate також збирає production Docker image, перевіряє VPS Compose/Caddy і збереження сесій та правил після реального перезапуску контейнера з постійним томом.

Черга забезпечує повторну доставку. Telegram не має клієнтського idempotency key для `sendMessage`: якщо API прийняло повідомлення, а процес завершився до запису підтвердження, можлива повторна доставка. Абсолютна гарантія «без жодних проблем» або exactly-once тут неможлива. Сервер мусить бути онлайн, API біржі — доступне, а користувач — не блокувати бота. JSON-перевірки — polling, тому коротке торкання ціни між перевірками може бути пропущене.

Документація: [Telegram Bot API](https://core.telegram.org/bots/api), [Telegram deep linking](https://core.telegram.org/bots/features#deep-linking), [Firebase ID token verification](https://firebase.google.com/docs/auth/admin/verify-id-tokens).
