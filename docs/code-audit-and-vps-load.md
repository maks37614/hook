# Перевірка коду й навантаження — 21 жовтня 2026

Перевірено поточний код `maks37614/hook` на основі `7a2bc17`: TypeScript, виробничу збірку, автоматичні тести, залежності, HTTP/WebSocket API, авторизацію, збереження даних, фоновий нагляд, біржові кеші та клієнтські оновлення. Автоматичні перевірки охоплюють увесь проєкт; ручний огляд зосереджено на сервері, спільних розрахунках і життєвому циклі даних. Це не гарантія відсутності всіх можливих помилок.

Частина проблем Vite належить до режиму розробки; цей сервер не використовує gRPC для автентифікації клієнтських сертифікатів. Після оновлення повний `npm audit` повідомляє про 0 відомих вразливостей на дату перевірки.

Джерела виправлених версій: [gRPC advisory](https://github.com/grpc/grpc-node/security/advisories/GHSA-m9gg-hp2v-232j), [Vite advisory](https://github.com/vitejs/vite/security/advisories/GHSA-rq7h-c2jc-7f22), [source-map-js advisory](https://github.com/advisories/GHSA-68fv-2mgg-jv7q).

Локально після виправлень: 260 тестів пройшли, виробнича збірка успішна, TypeScript `--noEmit` пройшов, `git diff --check` без помилок. Для локальної перевірки використано TypeScript 6 через обмеження запуску нативного TypeScript 7 у середовищі перевірки; репозиторій зберігає TypeScript 7 і окрему перевірку в GitHub Actions.

## Що вдалося виміряти на живому сайті

Окремі читання `https://h00k.top/api/health` та `/api/dom/status` отримали відповідь сервера. Він повідомив release `6726cf25fe46f7bee9eff1b184a4d9c268f70755`; поточний `main` до цих виправлень — `7a2bc17387c648518330d992122b71f3d6ec7e04`. Отже, встановлення коду, перевіреного в цьому аудиті, на VPS не підтверджене. Зміна репозиторію сама по собі не є перевіркою встановленої версії.

Посилання агента на `hook2` у перевіреному коді може пояснювати розбіжність версій; конфігурацію встановленого агента на VPS не читали. Для перенесення старого агента на `hook` потрібне одноразове встановлення його оновленої копії за [інструкцією для наявного клону](vps-auto-deploy.md). У межах цього аудиту VPS не переналаштовувався.

За інтервал між відповідями близько 64,2 с, приблизно 19:39–19:40 UTC:

| Джерело | Приріст лічильника | Приблизна частота |

Лічильники показують вихідні REST-запити до бірж. Вони не охоплюють WebSocket-повідомлення, HTTP-запити від відвідувачів, Telegram, CPU, RAM або дискові операції. На початку вимірювання Binance мав 3 активні й 8 запитів у черзі; наприкінці черги обох бірж були порожні, активної паузи бірж не було. Це короткий знімок, а не добовий моніторинг. Навантажувальних запитів на живий сайт не виконувалося.

## Локальний контрольний замір

Окремі виробничі процеси Node v24.19.0, 12 секунд прогріву й приблизно 60 секунд вимірювання. Docker використовує Node 22, тому числа не можна прямо переносити на VPS. Біржі замінено локальними відповідями: каталог із 75 інструментів, свічки, OI; для кожної активної унікальної пари — стакан по 200 рівнів з кожного боку, 10 оновлень стакана/с, 20 угод/с і 10 тикерів/с. Фонові cron-завдання працювали. Telegram був вимкнений, вкладки браузера та повний пошук щільностей не запускалися.

CPU — процесорний час основного Node-процесу за інтервал, де 100% означає одне повністю зайняте ядро. RSS — максимальна пам'ять основного процесу від запуску, включно з прогрівом; це не вся пам'ять контейнера чи VPS. Запуск імітації даних також додає власні витрати. Дані не визначають граничну кількість користувачів і не моделюють багатогодинну роботу.

| Сценарій | CPU одного ядра | Пікова RSS | Виклики fsync за хвилину |
| --- | ---: | ---: | ---: |
| Без користувацького нагляду, фоновий скринер працює | 0,9% | 143 MiB | 0 |
| 1 користувач, 10 різних пар у нагляді | 3,6% | 180 MiB | 40 |
| 10 користувачів × 10 тих самих пар, 100 записів нагляду | 13,7% | 227 MiB | 165 |

У двох активних сценаріях залишалося 10 спільних ринкових клієнтів, 30 тем і 2 фізичні з'єднання з імітованою біржею. Персональні стакани, конфігурації, сетапи та збереження стану продовжують вимагати ресурсів для кожного запису користувача. 100 записів нагляду не означають 100 відкритих вкладок чи 100 різних пар.

В окремому такому самому замірі без активного нагляду пікова RSS до відкладеного завантаження Vite була 335 MiB, після — 143 MiB. Це локальна різниця приблизно 192 MiB, а не підтверджена економія на VPS.

Візуалізація графіків та індикаторів переважно виконується в браузері; отримання й ретрансляція біржових даних проходять через VPS. Основний JS-файл після збірки має приблизно 2,55 MB, або 688 kB gzip: це помітно для першого завантаження браузера та трафіку, але не є постійним споживанням CPU сервера. Розбиття клієнтського пакета на частини залишається окремою можливістю оптимізації.

Частоти cron означають заплановані інтервали, а не гарантію завершення аналізу за цей час. При довгих чергах бірж перевірки можуть затримуватися. Спільний аналіз усуває частину дублювання, але не робить витрати на однакові пари незалежними від кількості користувачів.

## Як отримати фактичні CPU/RAM/диск VPS

На VPS, без зміни конфігурації або перезапуску:

```sh
docker stats --no-stream
free -h
vmstat 1 10
df -h
docker system df
```

Для репрезентативного результату потрібні кілька хвилин звичайної роботи та окремий замір під час нагляду, відкритого термінала й пошуку щільностей. `docker stats` показує пам'ять контейнера і накопичувальні мережеві/дискові лічильники; для швидкості обміну потрібно порівнювати два знімки за відомий інтервал. Слід врахувати також Caddy, систему й інші процеси VPS. У поточному Compose обмежень CPU/RAM для застосунку не задано.

SSH або показники Docker з VPS у цьому аудиті не були доступні. Точні CPU%, RAM, IOPS та запас місткості VPS залишаються невиміряними.
