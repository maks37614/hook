# HOOK Paper Bot: формації, реверс, АвтоСкальпінг

Окремий PHP-бот для OVH / звичайного хостингу. **Угоди віртуальні**, торгових API-ключів немає. Баланс, індикатори, рішення, журнал і звіти обчислюються на PHP-хостингу. Всі ринкові дані надходять **тільки з h00k.top**. Прямого fallback до бірж більше немає.

## Швидке оновлення існуючої інсталяції

1. Збережіть резервну копію приватного `state.php` через FTP. Це повна копія рахунку; CSV містить лише звіт.
2. Завантажте оновлений вміст `www` на PHP-хостинг, **зберігши свій `config.local.php` та приватний `data_dir`**. Архів не містить справжніх ключів або користувацьких даних. Папка `tests` для хостингу не потрібна.
3. Один раз оновіть серверну частину h00k.top до цього коміту: `server/paperFeed.ts`, `server/marketService.ts`, `server/marketTickerFeed.ts`. Захищений endpoint тепер має контракт **v2**. Попередній контракт v1 не містить свічок і для нової версії бота недостатній.
4. Залиште на VPS приватний `HOOK_PAPER_FEED_TOKEN`, а в кабінеті той самий токен. Окремі пароль кабінету й ключ cron не змінюються.
5. Перевірте, що h00k.top **вже збирає 1m-свічки потрібних монет**. Якщо штатний фоновий сканер наразі працює на `1h`, у VPS `.env` можна змінити **його існуюче** завдання:

   ```dotenv
   HOOK_SCREENER_TIMEFRAME=1m
   ```

   Це змінює таймфрейм одного сканера, не додає ще одного. Перезапустіть застосунок за вашим звичайним процесом. Для наявного Compose:

   ```bash
   docker compose -p hook2 -f compose.yaml -f compose.vps.yaml up -d --build
   ```

   Якщо потрібні формації цього самого фонового сканера, виберіть `1m` і на вкладці «Формації». Інші таймфрейми формацій можливі лише за наявності відповідного готового кешу сайту.
6. Збережіть щохвилинний cron. Дочекайтеся свіжого джерела й даних. Вкладка «АвтоСкальпінг» окремо вмикається кнопкою **«Запустити АвтоСкальпінг»**. Оновлення не вмикає її автоматично.

Стара історія, відкриті позиції й баланс мігруються автоматично без скидання. Старі угоди відображаються як «Формації». Рівні та витрати вже відкритих угод залишаються зафіксованими. **Не видаляйте файл рахунку для оновлення.**

## Джерело даних і навантаження VPS

Існуючий `/api/paper/formations` за тим самим окремим Bearer-токеном передає:

- готові формації обраного таймфрейму, до чотирьох кешованих вибірок;
- наявні котирування з оригінальним часом збору, до 25 основних пар на джерело та явно запитані інструменти;
- вже кешовані OHLCV-свічки: до 12 інструментів, до 6 таймфреймів, до 200 свічок на серію, до 72 серій.

Це **лише читання наявної пам’яті**: endpoint не викликає `fetchKlines`, сканер, AI, WebSocket або біржові API. Немає нових таймерів чи фонових розрахунків на VPS. Автотести перевіряють, що повторні експорти не додають мережевих запитів і не змінюють час збору джерела.

Нульового навантаження мережевий endpoint не має: залишається читання обмеженого кешу, серіалізація та передача JSON. PHP-бот робить **один запит до h00k.top за cron-запуск**, спільний для обох стратегій та всіх відкритих позицій. Навантаження саме вашого VPS не вимірювалося.

**Відсутніх даних endpoint не добуває.** Якщо h00k.top не збирає 1m-свічки певної монети, бот покаже очікування й не відкриватиме угоди. Готові браузерні fallback-дані, які ніколи не потрапили на сервер, також недоступні. Додавання монети у PHP не запускає її сканування на VPS.

Старші TF будуються на OVH з повних груп реальних хвилинних свічок або беруться з готового нативного кешу h00k.top. При пропуску хвилини агрегована свічка не створюється. Незакриті, майбутні, NaN та некоректні OHLC відкидаються. Немає синтетичних цін, інтерполяції прогалин або згенерованих результатів у користувацькому журналі.

У віртуальних розрахунках використовується реальна ринкова ціна плюс явно задана модель прослизання та комісій. Вік котирування обмежений налаштуванням; оригінальний час його збору збережений у позиції та CSV як `source_quote_utc`, без підміни поточним часом. Котирування, зібране до входу, не може створити наступний спостережений вихід. Це модель виконання, а не доказ виконання реального ордера на біржі.

## Вкладка «Формації» та реверс

Збережені штатні фільтри біржі, ринку, TF, обсягу, категорії, напрямку, статусу, пошуку, confidence, confluence та R:R. Обов’язкові початкові перевірки `passed`, `confirmed`, `closedCandleOnly`, `lookAheadSafe`, `enoughData`, `finiteData`, `breakoutConfirmed` і всі чотири `validation.filters`.

Реверс застосовується **після перевірки вихідного сигналу**, перед симульованим виконанням:

- LONG → SHORT; SHORT → LONG;
- старий target стає стопом; старий stop стає ціллю;
- ціна входу береться зараз, із прослизанням уже для фактичного нового напрямку;
- розмір позиції перераховується за фактичним стопом, ризиком і витратами;
- вихідні рівні зберігаються, а реверс позначається в історії, позиції та CSV.

Приклад **для пояснення**, не результат торгів: LONG entry=100, stop=98, target=106 перетворюється на SHORT зі stop=106 і target=98. Gross R:R стає близько 0,33, а не 3. Тому для реверсу є **окремий** мінімум R:R, типово 0,1; мінімальний R:R початкового сигналу й далі перевіряється. Від’ємний потенціал після витрат відхиляється. Мінімум не досягається пересуванням реальних рівнів.

Spot-short не моделюється: реверс LONG на spot буде відхилений. Одна формація виконується лише один раз, незалежно від подальшого перемикання реверсу. Для порівняння реверсу є окремий фільтр статистики. Реверс сам по собі не створює торгової переваги.

## Вкладка «АвтоСкальпінг»

Це хвилинна range-стратегія на реальних OHLCV, **не високочастотний тиковий скальпер**. Монети задаються USDT-символами через кому або автоматично вибираються з наявних котирувань h00k.top. За один цикл — до 8 монет і 1–3 TF входу (`1m`, `5m`, `15m`, `1h`), із окремим старшим TF.

Логіка входу:

1. Лой і хай визначаються за `lookback` попередніми **закритими** свічками, без сигнальної свічки в цьому вікні.
2. LONG потребує входу в нижню зону та закритої висхідної свічки вище підтримки й попереднього close; SHORT — дзеркально біля верхньої зони. Можна вимагати закриття за high/low попередньої свічки.
3. RSI Wilder: повернення з перепроданості/перекупленості, розворот в екстремумі або явно вимкнений фільтр. Окремі період і межі.
4. ATR Wilder, мінімум/максимум ширини діапазону, ліквідність за 24h та RVOL останньої закритої свічки проти попередніх 20.
5. Старші EMA: режим помірного тренду/діапазону, торгівля за напрямком EMA або явно вимкнена перевірка. Вікна старшого TF мають бути повними й свіжими.
6. Стоп — за мінімумом підтримки/сигнальної свічки з ATR-буфером; ціль — перед реальною протилежною межею. Буфери, мінімальний/максимальний стоп, допустиме відхилення ціни входу задаються в панелі.
7. Перевіряються **чистий R:R і чистий потенціал після двох комісій та несприятливого прослизання**. Невигідна ціль відхиляється, а не відсувається для красивого R:R.

Детальні захисти: ризик угоди, плече, кількість позицій, денний ліміт збитку, просадка всього рахунку, кількість входів на день, пауза після серії збитків, пауза між угодами монети, час торгової сесії та максимальна тривалість угоди. Ліміти дня й години використовують часовий пояс звітів.

Обидва боти мають **спільний баланс**, загальний ліміт позицій та відкритого ризику з вкладки «Формації». Дві позиції в одному інструменті одночасно не відкриваються. Оцінка ризику враховує комісії та задане стоп-прослизання; геп може дати більший збиток.

Таблиця діагностики показує розраховані лой/хай, ATR, RSI, RVOL і конкретну причину очікування. Якщо історії мало, потрібен прогрів. Наприклад, 30 свічок 15m — 450 хвилин реальної хвилинної історії; готовий кеш 15m скорочує очікування. Поточні числові значення — гіпотези для перевірки, не параметри з доведеною прибутковістю. Дослідження й джерела — у `SCALPING_RESEARCH.md` і в самій вкладці.

## Виходи, пропуски даних та витрати

Рівні, комісія і прослизання фіксуються при вході. Виходи перевіряються в часовому порядку за закритими **1m-свічками після хвилини входу**. Геп через стоп виконується за гіршим open; сприятливий геп через ціль не покращує її ціну. Якщо одна свічка торкається і stop, і target без доказу порядку в open, береться стоп з позначкою невизначеності.

Хвилина входу часткова: її high/low могли відбутися до входу, тому використовуються лише спостережені ціни. Коротке торкання між cron-запусками в цій хвилині може бути пропущене. Реальна черга ордерів, spread, funding, ліквідації, точність біржових лотів та ставки запозичення не моделюються. Spread не вигадується, якщо джерело його не передає.

На OVH утримується до 2160 останніх реальних 1m-свічок на інструмент і до 200 нативних свічок на старший TF. За пропуску потрібної хвилини курсор моніторингу не перескакується, нові входи блокуються. Якщо перерва старша за доступну історію, її не можна достовірно відновити з цього кешу. Діагностика залишається видимою; не видавайте таку історію за повний тест.

Максимальна тривалість скальп-угоди викликає `TIME_EXIT` за свіжою ціною після перевірки історичних стопів/цілей. Звичайне ручне закриття очікує перевірки хронології. При незворотній прогалині є окрема кнопка «Закрити з позначкою прогалини»: вона виконає ручний вихід за наступною свіжою ціною, запише `MANUAL_DATA_GAP` / `history_gap` і не видаватиме результат за підтверджений історичний стоп чи target. Без свіжої ціни навіть цей вихід не виконується. Пауза нових входів не зупиняє супроводження вже відкритих позицій — cron має працювати далі.

## Автоматична статистика

Є погодинні, денні, ISO-тижневі та місячні звіти, часовий пояс IANA, фільтри всіх ботів / формацій / лише реверсу / скальпінгу, CSV та пагінація.

Для кожного періоду: входи, закриття, перемоги/збитки/нуль, gross і net P&L, комісії, зміна грошового балансу, баланс на початок/кінець, win rate, profit factor, математичне очікування на закриту угоду, середній результат у R, середня тривалість, найкраща/найгірша угода та кількість неоднозначних виходів. Немає статистики з вигаданих угод.

Чистий P&L угоди відноситься до **закриття**, включаючи обидві комісії. Кожне фактичне списання комісії потрапляє у свій період. Тому net P&L і cashChange можуть відрізнятися при переході через межу періоду, але загальна зміна cash точно узгоджується з рахунком. Баланс — спільний рахунок навіть при фільтрі окремої стратегії. Відкритий P&L видно у загальних показниках еквіті; його не називають реалізованим.

Повторювана година під час переходу на зимовий час має окремий UTC-offset і не склеюється. Тижні використовують ISO-рік. Останні 200 періодів кожного виду кешуються автоматично cron; повний звіт та експорт відбудовуються з усієї збереженої історії. Просадка на головній панелі — лише за спостереженнями cron, не за кожним тиком.

## Перше встановлення, HTTP та cron

PHP **8.1+** зі стандартними JSON/OpenSSL/session/hash, вихідним HTTPS до h00k.top; cURL бажаний, є `allow_url_fopen` fallback. MySQL, SQLite, Composer і Node.js для PHP-частини не потрібні.

Скопіюйте `config.example.php` у `config.local.php`, задайте випадковий `setup_key` від 32 символів. Вкажіть `data_dir` **поза публічним DOCUMENT_ROOT**, із правом запису PHP. Типово це `.hook-paper-private` поруч із `www`. Не використовуйте `777`. Відкрийте сторінку, введіть ключ інсталяції та створіть власний пароль від 12 символів. Пароль зберігається лише як хеш. Стандартного спільного пароля немає.

Для вашого хостингу **без SSL** у приватному `config.local.php` підтримується:

```php
'require_https' => false,
```

Це дозволяє вхід і cron через HTTP; пароль, cookie сесії та cron-ключ на цьому з’єднанні будуть незашифровані. Вихідне джерело `source_url` залишається HTTPS, перевірка сертифікатів не вимикається. Існуючий `config.local.php` не перезаписується оновленням.

Зовнішній планувальник щохвилини викликає реальну адресу `cron.php`, показану у захищеному кабінеті:

```text
Method: GET або POST
Header: Authorization: Bearer ВАШ_ОКРЕМИЙ_CRON_КЛЮЧ
```

Ключ у query URL не підтримується. Без cron PHP не працює у фоні. Є `flock`, повторна перевірка ключа після отримання блокування та мінімальний інтервал 60 секунд. Локальний CLI: `php /повний/шлях/www/cron.php`.

OVH штатно описує найчастіший cron як раз на годину; для хвилинного моніторингу потрібен зовнішній HTTP cron або інший доступний щохвилинний планувальник. Джерело: https://docs.ovhcloud.com/en/guides/web-cloud/web-hosting/cron-tasks .

200 — `ok`/`too_soon`; 409 — вже виконується; 503 — бракує даних/джерело недоступне, слід прочитати діагностику. Помилка джерела не підміняється вигаданими цінами. 401 — неправильний ключ. Налаштування й CSV доступні лише після входу, форми мають CSRF, спроби входу обмежені.

## Місткість і резервні копії

До 10 відкритих позицій загалом, типово 5; до 1000 угод разом із відкритими; до 5000 ID виконаних сигналів; до 150 останніх подій. Історія угод автоматично не видаляється. За ліміту нові входи припиняються, моніторинг залишається. Файл стану обмежений 8 MB; на атомарну заміну потрібне місце ще для одного такого файла. При великому журналі потрібен PHP memory_limit щонайменше 128 MB. Інші файли/логи вашого хостингу також витрачають квоту 100 MB.

Зберігайте приватний `state.php` поза публічним сайтом. Він має негайний PHP `exit` перед JSON і атомарний запис під блокуванням. CSV — звіт, не повна резервна копія. Перед новою інсталяцією на іншому `data_dir` закрийте старі позиції, збережіть повний стан і експорт; старий рахунок не перезаписуйте.

## Перевірки

```bash
php www/tests/run.php
python3 www/tests/http_checks.py
node --import ./tests/fixtures/offline-network.mjs --import tsx --test tests/paper-feed.test.ts
```

PHP-тести покривають облік, реверс, індикатори, справжню схему джерела, агрегацію без прогалин, джерело без fallback, LONG/SHORT, стоп/target/time exit, ліміти ризику, міграцію, періоди через місяць/ISO-рік/DST та реальні HTTP-форми. Ринкові значення у тестових fixtures синтетичні лише для детермінованої перевірки коду; вони не додаються до робочого журналу та не доводять прибутковість стратегії.
